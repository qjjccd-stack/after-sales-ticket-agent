## 面试展开：用三个问题讲设计

**为什么有聊天记录还要业务记忆？** 聊天是完整交互证据，模型输入只保留有界窗口。业务记忆把型号、故障、已尝试步骤和当前工单明确保存，供模型、工具和回复生成共同使用，减少遗漏和重复排查。对照实验关闭跨轮业务记忆，保留聊天、摘要、当轮事实提取和检查点；没有另加“每轮从完整历史重建全部业务状态”的替代模块。

**为什么有检查点还要幂等？** 检查点记录流程到了哪里，业务幂等约束重复执行的效果。数据库提交成功后返回失败，重试仍可能走到同一个写入入口；原请求编号、唯一约束、事务和保存的执行结果共同避免重复建单。用户确认时同时复核身份、参数、有效期和工单版本，防止确认的内容与实际执行不一致。

**怎么定义任务成功？** 不是要求回答“已成功”就过关。FAQ 必须适用型号并有来源；确认前工单不变；确认后字段、状态、数量和审计符合预期；失败应如实返回，禁止操作不得改变数据。保留工具轨迹和当时数据库快照，再按业务契约自动评分。

## 不写进当前简历的结论

- 不写“上线服务真实客户”“企业级生产系统”“高并发平台”：当前是单实例 SQLite 的可部署演示版本，公网、容器和真实 HTTPS 验收尚待目标环境完成。
- 不写“上下文工程降低成本”：真实对照中开启记忆的总 Token 为 314,373，关闭组为 305,515，增加约 2.9%；本次没有评估完整历史与裁剪历史的成本差异。
- 不写“准确率提升 50%／线上成功率 100%”：固定场景运行通过率相差 50 个百分点，不能推广到实际业务分布。
- 不将旧版 41/50 → 50/50 描述为严格因果提升：旧迭代同时修改了实现和评分口径。
- 不写未实现的 MCP、多 Agent、向量数据库或微调；117 项测试是数量，不是覆盖率。
- 不使用未经确认的“独立从零开发”“带领团队”等归属。描述实现内容即可，面试如实说明官方模板与 AI 辅助开发。
