# 40 项增强实现清单

本次按原清单完整覆盖七类。表中“实现”指当前本机演示可用的功能；真实客服平台、公网部署、向量 RAG 均不在本版范围。

## 1. 工单业务（1–9）

| 编号 | 功能 | 实现与检查点 |
|---|---|---|
| 1 | 状态流转 | `actions.TRANSITIONS/validate_update` 五状态有限状态机，拒绝跳级；客户返工与维修确认分开检查 |
| 2 | 工单分派 | `choose_assignee` 按真实维修账号的型号、故障专长及未结束任务数推荐；管理员/客服可重分派 |
| 3 | 信息补充 | `supplement_ticket` 追加故障、联系方式、设备信息，保留原描述和前后快照 |
| 4 | 取消 | `cancel_ticket` 仅待处理可取消，确认后进入已关闭 |
| 5 | 优先级 | `priority_for` 安全故障紧急、多设备高、其余普通；人工调整限客服/管理员 |
| 6 | 查询筛选 | 编号、型号、状态、UTC 创建日期范围，最多 200 条并提示缩小范围 |
| 7 | 重复识别 | 同客户、同型号、未关闭工单，类别或文本相似；历史 other 类别从描述补判；重复建单需额外勾选 |
| 8 | 处理记录 | `ticket_events` 保存操作人、说明、前后状态；与业务事务同时提交 |
| 9 | 人工接管 | `handoff_ticket` 标记 manual 并写入原因，工作台可见；没有连接外部客服或通知系统 |

## 2. 上下文（10–16）

| 编号 | 功能 | 实现与检查点 |
|---|---|---|
| 10 | 持久会话 | SQLite 存完整可见对话、结构化事实和官方 AsyncSqliteSaver 检查点；刷新/进程重启恢复 |
| 11 | 会话 ID | `thread_id` 归属账号；`request_id` 标识一次请求；`ticket_id` 标识工单，另用 operation_id 标识确认 |
| 12 | 结构化记忆 | `TicketContext` 保存型号、问题、工单、尝试步骤、待操作和排查是否耗尽 |
| 13 | 裁剪 | `trim_conversation` 保留最近至多 6 个完整轮次及字符预算，不拆散工具调用与结果 |
| 14 | 历史摘要 | `finish_request` 保存最多 1800 字的早期用户信息摘录；不把摘要当权限或当前状态依据 |
| 15 | 历史关联 | `search_tickets(mine=True)` 按真实用户归属检索维修记录 |
| 16 | 指代 | 当前 ticket_id 只由实际工具/确认结果写入；已有型号复用，新型号明确出现时重置故障上下文 |

“已解决”等状态仍须重新读库，不能从记忆里直接回答。提取器不是通用自然语言理解系统，多设备和含糊表达可能仍需澄清。

## 3. FAQ 与检索（17–22）

| 编号 | 功能 | 实现与检查点 |
|---|---|---|
| 17 | 型号约束 | 工具拒绝与当前已知型号冲突的参数，检索先过滤 product_models 再计算匹配分数 |
| 18 | 故障分类 | network、bluetooth、power、offline、charging、screen、shipping、warranty、safety |
| 19 | 同义词 | `SYNONYMS` 将明确的配对/搜索不到等归类；单说“连不上”不擅自认定蓝牙 |
| 20 | 引用 | 固定回复展示 FAQ 编号、适用型号与本地资料来源 |
| 21 | 无资料 | 返回 no_matching_faq，拒绝把 X200 专用蓝牙资料用于 X100 |
| 22 | 全文排序 | 纯 Python BM25，英文词与中文双字片段；无需向量库或独立搜索服务 |

资料仍为 4 条模拟 FAQ。增加型号和类别要同步维护 FAQ；未覆盖的故障只建单/转人工，不编造维修步骤。

## 4. 工具执行（23–29）

| 编号 | 功能 | 实现与检查点 |
|---|---|---|
| 23 | 执行层确认 | 模型只 `propose`；页面 `confirm_action` 绑定用户、会话、请求、动作、冻结参数、15 分钟有效期及工单版本 |
| 24 | 真实结果回复 | `finalize/render_result` 按工具结果和再次读库生成业务文本；替换模型的未验证最终消息 |
| 25 | 权限 | `actor_in/visible/validate_update` 在提案、查询、确认时校验真实账号；模型工具 schema 不暴露身份字段 |
| 26 | 统一错误 | success/action/error_code/retryable；参数错误、数据库忙、无资料、权限不足可区分 |
| 27 | 审计 | 工具调用记录 execution_events，业务变更 ticket_events；确认结果与变更同事务 |
| 28 | 超时重试 | 模型请求最多一次瞬时错误重试，每次记账；整轮 100 秒、单次 35 秒；写操作依赖同 operation_id 幂等确认，不盲目重放 |
| 29 | 预算 | 每请求模型最多 4 次、工具最多 8 次、输出最多 900 token；输入字符裁剪与 16,000 token 近似预检，失败重试保留累计用量 |

所有七个写工具都经过同一个确认入口。数据库中保存确认参数的 SHA256 是防止流程内参数变化的校验；它不声称能抵御有权限任意篡改整个本地数据库的人。

当前外部调用只有模型 API；SQLite 有 busy_timeout，业务写入事务可回滚。Token 服务端分词和 schema 开销存在差异，预检不是精确账单上限。配置单价后才显示金额。

## 5. 多轮诊断（30–33）

| 编号 | 功能 | 实现与检查点 |
|---|---|---|
| 30 | 信息收集 | 缺型号或问题时确定性追问，已提供内容写入结构化事实 |
| 31 | 分步骤排查 | 型号/类别检索，每轮最多展示一条可靠、未尝试步骤 |
| 32 | 已尝试记录 | 明确失败反馈绑定上一条实际展示步骤；不会把模型自己编造的动作写为用户已完成 |
| 33 | 升级售后 | 记录已验证步骤耗尽，后续直接建议建单/人工；用户明确要求且字段齐全时可直接进入确认 |

不强迫用户先做完排查才能申请工单。没有现有工单时，人工接管先通过建单确认取得真实编号。

## 6. 评测（34–37）

| 编号 | 功能 | 实现与检查点 |
|---|---|---|
| 34 | 状态一致 | 对每条可见回复保存其时刻的数据库快照，避免把确认前查询与确认后状态混为一次断言 |
| 35 | 长对话 | 50 场景包含连续 10 轮诊断后建单，检查型号、原始故障、已尝试步骤与耗尽状态 |
| 36 | 越权/异常 | 禁止建单、伪造确认参数、调用不存在工具、客户越权、其他用户查询、错误型号、过期及篡改、版本冲突 |
| 37 | 质量与成本 | 任务完成数、状态一致数、合法工具调用数、耗时、服务端 token 和可选单价；保留逐轮原始证据和源文件指纹 |

任务成功必须符合预期业务状态。“被正确拒绝”的越权场景也算任务通过，但该非法调用不计合法工具调用。状态一致性采用明确陈述的规则检查，不能覆盖任意自然语言语义；不用另一个 LLM 充当裁判。离线脚本模型结果和真实模型结果分别报告。

## 数据兼容与运行边界

旧工单只增列，不删除、不改编号；旧记录归属 legacy，只供工作人员查看，避免自动分给新注册的客户。账号、会话、工单、审计和检查点共用一个 SQLite 文件。客户隔离在业务查询里强制执行，不依赖页面过滤。

当前认证用于本机演示，登录令牌在 URL 中恢复会话。公网部署需要另行设计 Cookie/统一认证、访问限制与部署策略；本次只监听 127.0.0.1。FAQ 来源和示例账号属于演示数据，真实模型评测和浏览器验证均使用隔离数据库。
